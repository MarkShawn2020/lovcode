# ADR-0001：Ataru 搜索采用本地优先的模块化单体

- 状态：已接受
- 日期：2026-08-10
- 决策范围：产品边界、搜索内核、公开契约与迁移方式

## 背景

Lovcode 已能读取 Claude Code、Codex 等来源的本地会话，并提供全文与语义搜索，但产品同时承担工作台、运行时管理和历史查看，主路径不够聚焦。Ataru 将把这部分能力收敛为“从过去的 AI 对话中找回可用上下文”的独立产品。

产品边界如下：

- **Ataru 负责过去**：采集、索引、检索、聚合和打开已经发生的对话。
- **Yoda 负责现在**：创建、执行、监控和续接正在进行的 Agent 工作。
- Ataru 可以复制或交接已找回的上下文，但不拥有 Agent 执行状态、终端生命周期或任务编排。

核心产品指标是 **TTCR（Time To Correct Recall，正确召回耗时）**，即从用户开始搜索，到第一次确认并打开或使用足以支持下一步工作的正确历史上下文所经历的时间。搜索延迟、索引新鲜度和排序质量都是 TTCR 的驱动指标，而不是其替代品。

我们需要同时满足：

- 兼容已有会话解析、索引、Tauri 命令和本地数据，不做一次性重写。
- 关键字搜索 p95 不超过 100 ms；混合搜索 p95 不超过 800 ms。
- 输入响应 p95 不超过 50 ms；新增内容可检索的新鲜度 p95 不超过 2 s。
- 标注评测集上 Recall@10 不低于 0.90，MRR@10 不低于 0.75。
- 默认本地工作；外部 Embedding 必须显式启用，并且随时可以退回纯关键字路径。

## 决策

### 1. 采用单进程模块化单体

Ataru 保持在 Tauri/Rust 单进程内运行，不引入本地微服务或常驻网络服务。搜索内核划分为三个有明确依赖方向的模块：

- `sdk`：拥有 v1 请求、响应、实体标识、错误码和端口定义；不依赖 `api`、`ai`、Tauri、文件系统或网络实现。
- `api`：Tauri/CLI 入口，负责校验、时限、模式选择、编排、降级、版本协商和观测；依赖 `sdk`，通过端口调用索引与来源适配器。
- `ai`：负责查询意图判断、Embedding、语义召回、融合与重排；只依赖 `sdk` 的类型和端口，不直接读取 UI 或原始会话文件。

现有解析器、Tantivy 索引和语义存储先作为兼容适配器留在边界后方，随后按测量结果逐步拆分。`sdk` 不得反向引用实现模块。

### 2. 使用一个版本化搜索契约覆盖三种召回粒度

公开入口为 `ataru_search` v1。请求以 `level` 指定聚合粒度：

- `turn`：一个用户提示及其后续 Assistant/工具消息，直到下一个用户提示。
- `session`：同一来源会话内的所有命中。
- `project`：同一规范化项目下所有会话的命中。

请求以 `mode` 指定 `auto | keyword | semantic | hybrid`。响应同时返回 `requestedMode` 与实际执行的 `mode`，并用 `warnings` 明确说明降级；因此客户端不能把“语义不可用后的关键字结果”误标为混合结果。

v1 只提供有限 Top-K（最多 100 条），不承诺完整命中计数或分页。新增可选字段保持向后兼容；字段移除、含义变化或标识规则变化必须发布新的主版本。

### 3. 采用本地优先、可丢弃索引

原始会话文件始终是事实来源，Ataru 默认只读。全文索引、向量、缓存和清单都是可重建的派生数据：

- 构建新索引后原子切换，失败时继续使用上一个健康版本。
- 文件监听负责低延迟增量更新，周期性清单对账负责修复漏事件。
- 删除、移动和权限变化通过 tombstone 与对账传播，避免幽灵结果。
- 关键字搜索不依赖 AI 配置或网络。

### 4. 采用渐进替换而非大爆炸迁移

新契约先包住旧实现，再以契约测试、影子查询和固定评测集逐层替换。旧命令在至少两个稳定版本内保留；只有调用量归零、结果差异已解释且性能门槛通过后才下线。索引格式升级通过版本化清单触发重建，不迁移或改写原始对话。

### 5. 把隐私和降级写入契约

- 默认模式完全本地，不上传查询、路径或历史内容。
- 远程语义能力必须由用户显式配置；启用界面要说明查询与待向量化文本可能离开设备。
- 外发前最小化文本，并默认排除二进制、原始工具结果和思考块，执行凭据样式脱敏。
- API Key、原始查询、正文片段和完整路径不得进入日志或遥测。
- 语义超时、限流、配置缺失或索引过期时自动回退关键字并返回机器可读警告；两条路径都不可用时返回稳定错误，绝不把故障伪装成“零结果”。

详细契约、SLO、故障矩阵和阶段门槛见 [Ataru 搜索架构](../architecture/ataru-search-architecture.md)。

## 影响

### 正面

- 单进程调用避免 IPC/网络开销，符合桌面搜索的延迟目标。
- 稳定 `sdk` 契约使 React、CLI 和未来调用方共享相同语义。
- 兼容适配器降低重构风险，原始数据无须迁移。
- 关键字路径始终独立，AI 能力可以增强体验而不会成为可用性前提。
- 三种聚合粒度直接支持“找一句话、找一次会话、找一个项目”的用户意图。

### 负面

- 单进程内的模块故障隔离弱于独立服务，必须用超时、任务边界和资源上限约束 AI 与索引工作。
- 兼容期会同时维护新旧 API，并承担影子比较和双路径测试成本。
- 增量全文索引与向量索引存在短暂不一致，需要在响应中暴露实际模式和新鲜度状态。
- 远程 Embedding 即使显式启用仍有内容出域风险，需要持续维护脱敏和数据边界。

### 中性

- 派生索引格式可以快速演进，但每次不兼容升级都可能触发后台重建。
- `project`、`session`、`turn` 是公开领域语义；底层 Message 仍是证据单元，不作为独立搜索产品层级。

## 备选方案

### 继续把 Lovcode 作为综合工作台

不采用。运行中任务与历史召回的用户意图、状态模型和成功指标不同，会继续稀释 TTCR 主路径。

### 一次性重写搜索与所有来源解析器

不采用。现有多来源兼容行为难以一次复刻，且无法通过小步影子对比控制回归。

### 拆成本地微服务或云端搜索服务

暂不采用。当前桌面规模和团队规模不足以抵消部署、升级、认证、离线可用性和隐私成本。只有单进程在真实基准上持续无法满足资源隔离或规模目标时才重新评估。

### 只保留语义搜索

不采用。代码符号、错误串、路径和精确引用更适合关键字检索；语义提供方还会带来网络、成本与隐私依赖。

### 维持无版本的旧命令结构

不采用。它会把聚合、降级和字段解释散落到每个客户端，使后续替换底层实现变成破坏性变更。

## 复审条件

出现以下任一事实时复审本 ADR：

- 参考数据规模下，单进程方案经过画像与优化后仍持续无法满足延迟或内存门槛。
- 需要多个独立产品同时写入同一索引，单写者模型不再成立。
- 法规或客户策略禁止任何形式的远程文本向量化。
- Ataru 开始承担运行中 Agent 编排，导致与 Yoda 的边界失效。
